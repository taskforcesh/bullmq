On this page

Introduction ​

BullMQ for Go is the official Go port of BullMQ. It runs the exact same Lua scripts (Redis™) and SQL (PostgreSQL) as every other BullMQ SDK, so a queue produced by the Node.js library can be consumed by a Go worker and the other way round.

The module has three packages:

  • bullmq: Queue, Worker, Job, QueueEvents, FlowProducer and job schedulers. It only depends on a Backend interface and imports no datastore driver.
  • redisbackend: the Redis backend, built on go-redis v9.
  • postgresbackend: the PostgreSQL backend, built on pgx v5.

Installation ​

bash
go get github.com/taskforcesh/bullmq-go

BullMQ for Go requires:

  • Go 1.26 or newer
  • Redis 6.2 or newer, or PostgreSQL 13 or newer

Both backends ship in the module, but a program only links the driver of the backend package it imports.

Get started ​

BullMQ for Go uses context.Context for cancellation and goroutines for concurrency: a worker processes each job on its own goroutine, and a Queue can be shared by any number of goroutines.

Adding jobs to a queue ​

go
package main

import (
	"context"
	"log"

	bullmq "github.com/taskforcesh/bullmq-go"
	"github.com/taskforcesh/bullmq-go/redisbackend"
)

func main() {
	ctx := context.Background()

	backend := redisbackend.New(redisbackend.Options{Addr: "127.0.0.1:6379"})
	queue, err := bullmq.NewQueue("emails", &bullmq.QueueOptions{Backend: backend})
	if err != nil {
		log.Fatal(err)
	}
	defer queue.Close()

	job, err := queue.Add(ctx, "welcome", map[string]string{"to": "ada@example.com"}, &bullmq.JobOptions{
		Attempts: bullmq.Int64(3),
		Backoff:  &bullmq.Backoff{Type: bullmq.BackoffExponential, Delay: 1000},
	})
	if err != nil {
		log.Fatal(err)
	}
	log.Printf("added job %s", job.ID)
}

The Backend option is required: it is a factory such as the one redisbackend.New or postgresbackend.New returns. Job data is encoded with encoding/json.

Processing jobs ​

A worker hands each job to a processor, a func(ctx context.Context, job *bullmq.Job) (any, error). The value it returns is stored as the job's return value, and an error fails the attempt (the job is retried while attempts remain):

go
package main

import (
	"context"
	"errors"
	"log"
	"os"
	"os/signal"
	"syscall"

	bullmq "github.com/taskforcesh/bullmq-go"
	"github.com/taskforcesh/bullmq-go/redisbackend"
)

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	backend := redisbackend.New(redisbackend.Options{Addr: "127.0.0.1:6379"})
	worker, err := bullmq.NewWorker("emails", func(ctx context.Context, job *bullmq.Job) (any, error) {
		var payload struct {
			To string `json:"to"`
		}
		if err := job.DecodeData(&payload); err != nil {
			return nil, bullmq.NewUnrecoverableError("invalid payload: %v", err)
		}
		log.Printf("sending a welcome email to %s", payload.To)
		return map[string]bool{"sent": true}, nil
	}, &bullmq.WorkerOptions{Backend: backend, Concurrency: 10})
	if err != nil {
		log.Fatal(err)
	}
	defer worker.Close()

	// Run blocks until ctx is cancelled or Close is called.
	if err := worker.Run(ctx); err != nil && !errors.Is(err, context.Canceled) {
		log.Fatal(err)
	}
}

Cancelling the context of Run, as Ctrl+C does here, stops the worker immediately: the jobs in flight see their context cancelled and are recovered later by the stalled check. worker.Close() stops it gracefully, waiting for them. See Workers.

Listening to events ​

A worker publishes the lifecycle of its jobs on worker.Events(), and QueueEvents reads the events of every worker of the queue, in any language:

go
go func() {
	for ev := range worker.Events() {
		switch ev.Type {
		case bullmq.EventCompleted:
			log.Printf("job %s completed with %v", ev.Job.ID, ev.Result)
		case bullmq.EventFailed:
			log.Printf("job %s failed: %v", ev.Job.ID, ev.Err)
		}
	}
}()

See Workers and Queue Events.

Using PostgreSQL ​

Only the backend changes:

go
backend := postgresbackend.New(postgresbackend.Options{
	ConnString: os.Getenv("DATABASE_URL"), // e.g. postgres://localhost:5432/app
})
queue, err := bullmq.NewQueue("emails", &bullmq.QueueOptions{Backend: backend})
if err != nil {
	log.Fatal(err)
}
defer queue.Close()

The bullmq schema is created and migrated by the first operation. See PostgreSQL.

Connection configuration ​

redisbackend.Options holds the Redis settings: Addr (localhost:6379 by default), Username, Password, DB, PoolSize, and the key Prefix (bull by default, as in every other SDK):

go
backend := redisbackend.New(redisbackend.Options{
	Addr:     "redis.example.com:6379",
	Username: "app",
	Password: os.Getenv("REDIS_PASSWORD"),
	Prefix:   "myapp",
})

Each queue, worker and QueueEvents built from such a backend opens its own connections. To share a connection pool, or to set what Options doesn't expose such as TLS, pass an existing go-redis client. BullMQ never closes a client it didn't create:

go
rdb := redis.NewClient(&redis.Options{
	Addr:      "redis.example.com:6380",
	Password:  os.Getenv("REDIS_PASSWORD"),
	TLSConfig: &tls.Config{MinVersion: tls.VersionTLS12},
})
defer rdb.Close()

backend := redisbackend.New(redisbackend.Options{Client: rdb})

Workers and QueueEvents still run their blocking reads on a dedicated client, derived from the options of a *redis.Client (one connection) or a *redis.ClusterClient (one connection per node), so that a blocked read never holds a connection of the shared pool. A *redis.Ring can't be cloned, so its blocking reads share its pool. Backend() on a queue, worker, QueueEvents or FlowProducer returns its backend; a *redisbackend.Backend exposes Client() and BlockingClient().

Auto-pipelining ​

AutoPipeline (experimental) sends the backend's non-blocking commands through go-redis's automatic pipeliner, which writes the commands that concurrent goroutines issue at the same time together, as ioredis does for Node.js. It helps workers with a Concurrency above 1 and producers that add jobs from many goroutines, especially when Redis is remote. Use the full-duplex mode; go-redis's default mode runs one batch at a time and was slower in our benchmark:

go
backend := redisbackend.New(redisbackend.Options{
	Addr:         "127.0.0.1:6379",
	AutoPipeline: &redis.AutoPipelineOptions{FullDuplex: true},
})

A queued command doesn't observe its context's cancellation or deadline, and after a connection error go-redis may send a command again whose reply was lost, which can run a BullMQ command twice (as with a plain client). go-redis can change these options in a minor release. See the README for the details.

Interoperability ​

The Go SDK uses the same Lua scripts, SQL, key names and data layout as the Node.js, Python, Elixir, PHP, Rust and .NET SDKs. As long as both sides use the same Redis prefix, or the same PostgreSQL database and schema:

  • jobs added in any language can be processed by Go workers, and the other way round; data and return values are JSON;
  • retries, backoff, priorities, removal policies, flows, deduplication and rate limits behave the same whichever runtime processes the job (a custom backoff type needs a BackoffStrategy on Go workers);
  • QueueEvents in any language sees the events of Go workers;
  • job schedulers created in one language are advanced by the workers of the others.

Testing ​

Run integration tests against a real Redis or PostgreSQL server, with a unique queue name per test, and remove the queue afterwards:

go
func TestWelcomeEmail(t *testing.T) {
	ctx := context.Background()
	backend := redisbackend.New(redisbackend.Options{Addr: "127.0.0.1:6379"})
	name := fmt.Sprintf("emails-test-%d", time.Now().UnixNano())

	queue, err := bullmq.NewQueue(name, &bullmq.QueueOptions{Backend: backend})
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() {
		_ = queue.Obliterate(context.Background(), &bullmq.ObliterateOptions{Force: true})
		_ = queue.Close()
	})

	worker, err := bullmq.NewWorker(name, sendWelcome, &bullmq.WorkerOptions{Backend: backend})
	if err != nil {
		t.Fatal(err)
	}
	go func() { _ = worker.Run(ctx) }()
	t.Cleanup(func() { _ = worker.Close() })

	job, err := queue.Add(ctx, "welcome", map[string]string{"to": "ada@example.com"}, nil)
	if err != nil {
		t.Fatal(err)
	}
	deadline := time.Now().Add(10 * time.Second)
	for {
		state, err := queue.JobState(ctx, job.ID)
		if err != nil {
			t.Fatal(err)
		}
		if state == bullmq.StateCompleted {
			return
		}
		if time.Now().After(deadline) {
			t.Fatalf("job is %s, want completed", state)
		}
		time.Sleep(20 * time.Millisecond)
	}
}

To unit test a processor on its own, call it with a &bullmq.Job{Data: ...} built in the test. Methods that reach the datastore, such as UpdateProgress, return bullmq.ErrNoContext on such a job.

Limitations ​

  • No telemetry (OpenTelemetry) integration yet.
  • Redis Cluster is lightly tested and Sentinel untested: a cluster or failover client can be passed as Client, but CI only runs against a standalone server (the cluster tests run when REDIS_CLUSTER_ADDRS is set).
  • On PostgreSQL, QueueEvents can miss events when several jobs finish at once, in every SDK, until #5183 is fixed.
  • Job schedulers with a time zone read the system's time zone database; in containers without one, add import _ "time/tzdata" to the program.
  • Legacy repeatable jobs and sandboxed processors aren't supported.

The feature parity table lists what is and isn't implemented, and the Go README is the complete guide, including the changes from the pre-release API.
