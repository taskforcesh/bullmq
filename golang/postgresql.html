PostgreSQL ​

The postgresbackend package runs the same Queue, Worker, QueueEvents, FlowProducer and job scheduler API on PostgreSQL 13 or newer. It uses the schema and SQL that the Node.js, Python, Elixir and .NET SDKs use, so they all work on the same queues. Read the PostgreSQL backend guide for how the backend works and how it performs.

go
backend := postgresbackend.New(postgresbackend.Options{
	ConnString: os.Getenv("DATABASE_URL"), // e.g. postgres://localhost:5432/app
})

queue, err := bullmq.NewQueue("emails", &bullmq.QueueOptions{Backend: backend})
if err != nil {
	log.Fatal(err)
}
defer queue.Close()

worker, err := bullmq.NewWorker("emails", sendWelcome, &bullmq.WorkerOptions{
	Backend:     backend,
	Concurrency: 10,
})
if err != nil {
	log.Fatal(err)
}
defer worker.Close()

Options ​

OptionDefaultMeaning
ConnStringA pgx connection string, URL or keyword/value. Required unless Pool is set
SchemabullmqThe schema the queues live in, as the key prefix on Redis
PoolSize20Size of the query pool, unless the connection string sets pool_max_conns. Connections open on demand (pool_min_conns / pool_min_idle_conns are ignored for shared pools)
PoolA *pgxpool.Pool to use instead of ConnString; BullMQ never closes it. Its OnNotification/OnNotice callbacks aren't used on BullMQ's LISTEN connections
SkipVersionCheckfalseSkip the PostgreSQL 13 check
SkipMigrationsfalseDon't migrate: the schema must already be up to date (see Migrations)

Migrations ​

The first operation of the process reads the schema's migration ledger, which the other SDKs share, and unless it is up to date creates or migrates the schema, in one transaction under the advisory lock every SDK uses. Every new backend checks the ledger, and a schema that requires a newer BullMQ major version is refused with a *postgresbackend.SchemaVersionError:

go
var versionErr *postgresbackend.SchemaVersionError
if _, err := queue.Add(ctx, "welcome", data, nil); errors.As(err, &versionErr) {
	log.Fatalf("upgrade bullmq-go: schema %s requires major version %d", versionErr.Schema, versionErr.Required)
}

An up-to-date schema needs no DDL, so the application's role doesn't need to own it. It needs USAGE and CREATE on the schema (each queue gets a job id sequence on first use) and SELECT, INSERT, UPDATE and DELETE on its tables and sequences. To migrate as a deployment step, as the Node.js backend does with runMigrations, run postgresbackend.Migrate with a role that owns the schema, and set SkipMigrations in the application, which then refuses a schema that isn't up to date:

go
// At deployment, as the schema owner.
if err := postgresbackend.Migrate(ctx, postgresbackend.Options{ConnString: ownerURL}); err != nil {
	log.Fatal(err)
}

// In the application.
backend := postgresbackend.New(postgresbackend.Options{ConnString: appURL, SkipMigrations: true})

INFO

The Node.js backend only migrates when runMigrations is called, while the Go backend migrates on first use unless SkipMigrations is set, as the .NET one does. A schema migrated by any SDK can be used by the others. Schemas migrated by early .NET releases, which used a bullmq_migration ledger, are adopted.

Connections ​

  • Queries run on a pgxpool pool. Backends built with the same ConnString, Schema and PoolSize share one pool per process, which closes its idle connections when the last of them closes.
  • Each worker and QueueEvents also holds one dedicated connection, outside the pool, that LISTENs for new jobs or events, so an idle worker wakes up as soon as a job is added instead of polling. Size the server's max_connections for the pool plus one connection per worker and listener.
  • The application_name of a worker's dedicated connection is <queue> or <queue>:w:<worker name>, as in Node.js; queue.Workers lists them. PostgreSQL stores each non-ASCII byte of it as a 4-byte \xhh escape (é becomes \xc3\xa9; before PostgreSQL 16, a ?), which queue.Workers undoes, and then truncates it to 63 bytes, so the workers of a queue with a long name may be missing, and long worker names are truncated.

To use your own pool, set its search_path to the schema, since BullMQ doesn't change the session of connections it doesn't own:

go
config, err := pgxpool.ParseConfig(os.Getenv("DATABASE_URL"))
if err != nil {
	log.Fatal(err)
}
config.ConnConfig.RuntimeParams["search_path"] = "bullmq"
pool, err := pgxpool.NewWithConfig(ctx, config)
if err != nil {
	log.Fatal(err)
}
defer pool.Close()

backend := postgresbackend.New(postgresbackend.Options{Pool: pool})

The backend of a queue built with postgresbackend.New is a *postgresbackend.Backend, which exposes Pool() and Schema().

Differences from Redis ​

  • Pausing a queue sets a flag: the waiting jobs stay waiting and are counted as waiting.
  • Prioritized jobs are waiting jobs with a priority, reported as prioritized.
  • Children are keyed <queue>:<id> instead of <prefix>:<queue>:<id>.
  • Event ids are numbers instead of Redis stream ids.
  • Job data, return values and progress are stored as jsonb: a job read back holds equal JSON values, but not necessarily the same bytes (Job.Data, Job.ReturnValue), so decode them rather than compare bytes.
  • Deadlocks (40P01), serialization failures and connection errors are transient: a worker reports a failed fetch as an EventError and fetches again 5 s later, and retries finishing a job.

Known issues ​

These issues are in the SQL every SDK shares, and are tracked upstream:

  • #5160: a keep-count of 0 deletes every finished job of the queue. Go workers avoid it, removing only the finished job for bullmq.RemoveAll() and KeepCount(0), but jobs finished by other SDKs on the same schema are still affected.
  • #5183: QueueEvents can miss events when several jobs finish at once. See Queue Events.
  • #5184: .NET workers name their connections differently, so queue.Workers doesn't list them.
  • #5185: fetching can deadlock while promoting delayed jobs under concurrent workers. A Go worker reports it and fetches again.
